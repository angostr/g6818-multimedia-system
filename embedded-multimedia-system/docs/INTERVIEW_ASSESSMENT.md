# 面试官视角：项目评估与竞争力提升方案（v1.5 对齐）

> 评审对象：`embedded-multimedia-system`（基于 GE6818 / S5P6818 的 Framebuffer + MPlayer 从模式嵌入式多媒体系统，纯 C、模块化）。
> 评审立场：**专业嵌入式 / Linux 系统开发面试官**。
> 范围说明：**v1.5 起项目聚焦「视频播放器 + 电子相册」两大媒体应用**，原环境传感器（GY39 / LED / 蜂鸣器）相关模块已移除，本文档仅针对当前代码范围评估。

## 0. 一句话电梯演讲（记忆点，建议背熟）

> 「我用纯 C，在**没有任何 GUI 框架**（无 QT / 无 SDL）的 ARM Linux 上，写了一个带触摸手势交互的多媒体终端：用 **epoll 把『触摸输入』和『外部解码器子进程退出』两类事件统一调度**，再用手绘的**半透明控件**叠加在解码器渲染的画面上；并集成 BMP 解码与自绘 Framebuffer 图形栈。」

这句话的杀伤力在于：**具体、有技术名词、点出了「无框架」这一差异化、且把最亮的点（epoll 统一事件）放在最前面**。

## 1. 项目本质：面试官会怎么归类你

| 你以为的标签 | 面试官第一反应 | 真实该讲的价值 |
|---|---|---|
| 「我做了一个视频播放器」 | 「不就是调个 MPlayer 吗？」 | 你做的是**应用层 + 嵌入式 Linux 系统编程**：Framebuffer GUI、输入子系统手势、多进程 IPC 编排 |
| 「嵌入式多媒体系统」 | 「课设通用名，没记忆点」 | **无窗口系统的轻量级人机交互中间件**——工业 HMI / 车载中控的真实需求 |

**结论**：本项目的真正含金量**不在于「播放视频」**，而在于你独立实现了**底层图形栈与系统编程整合**。把叙事从「播放器」抬到「交互框架」，是打动面试官的第一杠杆。

## 2. 核心功能亮点

1. **自绘 Framebuffer GUI**：点 / 线 / 矩形 / 圆 / 字模 / Alpha 半透明混合，零第三方依赖。
2. **触摸手势引擎**：基于 input 子系统原始事件，四向滑动 + 点击判定。
3. **多进程媒体编排**：`fork + pipe + MPlayer slave mode`，主进程与解码器解耦。
4. **统一事件调度**：`epoll + SIGCHLD 自管道`，把信号转成 I/O 事件。
5. **BMP 解码**：二进制文件解析基本功（含 4 字节行对齐处理）。

## 5. 薄弱环节与自圆其说

### 5.1 架构定位：视频「播放器」包装
- `mplayer.c` 本质是 `fork` 出 MPlayer 子进程、通过管道发文本命令。**真正的编解码 / 缩放 / fb 写入全在 MPlayer 里**。
- 面试官第一问几乎必是：「视频解码是你自己写的吗？」答不好会显得「项目空心」。
- **必须**把叙事抬到「应用层 + 系统编程整合」，并讲清 MPlayer 内部管线（demux → decode → scale → fb write）及你的代码处于哪一层。

### 5.2 退出与资源回收
- v1.4 修复：返回菜单改设 `g_request_menu` 避免双重 `lcd_close`；`signal(SIGCHLD, SIG_DFL)` 复位信号处理；`quit_mplayer` 补 `fclose(mplayer_stdin)` 修复 `FILE*` 泄漏。遗留：仍无显式 `SIGINT` 处理（kiosk 场景可接受）。

### 5.3 硬编码与可配置性
- 视频列表 `videopath[]`、相册 `pathname[]`、设备名、UI 坐标全硬编码。可改为 `argv` / 配置文件 / 目录扫描提升通用性。

### 5.4 颜色 / 字节序隐患
- 用 `int` 打包 ARGB 写入 fb，未显式匹配 framebuffer 的像素格式（`FBIOGET_VSCREENINFO` 的 `var.bits_per_pixel` / RGB 排列）与主机字节序。测试图恰好掩盖，**彩图 / Alpha 可能串色**。

### 5.5 格式单一 / 测试空白
- 仅支持 BMP，无 JPEG / PNG → 相册实用性受限。
- 现已补 CI（语法检查 + 交叉编译），但**仍无单元测试**。

## 6. 面试防御清单（必考题 + 标准答法）

| 面试官可能问 | 标准答法要点 |
|---|---|
| 「视频解码是你写的吗？」 | 否，用 MPlayer 做解码 / 渲染引擎；我负责应用层、GUI、手势、IPC 编排——这是终端产品真实分工 |
| 「为什么 epoll 而非多线程？」 | 事件源少（触摸 + 子进程退出），单线程事件循环更简单、无锁、易推理；多线程要处理竞态 |
| 「为什么不用 signalfd？」 | 自管道可移植、易讲清「信号安全写」原理；若纯 Linux 生产环境我会用 signalfd 更优雅 |
| 「两套手势为什么不一致？」 | 已统一为「右滑 = 下一个 / 下一张，左滑 = 上一个」全局一致，并抽离 `GESTURE_TAP` 点击检测（v1.4 完成） |
| 「双缓冲其他模式 flush 谁做的？」 | 已统一为每帧 `lcd_flush()`；双缓冲本用于视频叠加防撕裂，现已规范刷新职责 |
| 「MPlayer 是外部进程，IPC 可靠吗？」 | 文本 slave 协议 + `fflush` 立即下发；可扩展为带 ack / 超时的指令队列 |
| 「解码卡顿怎么排查？」 | `top/perf` 看 CPU；确认 `-vf scale` 参数与 fb 分辨率匹配；排查 framebuffer 写入带宽 |
